# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Desktop catalog app for an industrial print shop (imprenta). Users log in with an individual account and, depending on their permissions, search a product catalog by name or code (e.g. "tangram" or "3072") and open a technical spec sheet (ficha técnica) with a reference image, material, category, description, and a flexible list of specs — this base catalog view is open to every authenticated user, no extra permission needed. From the ficha técnica, two permission-gated buttons open internal-only info: **Plásticos** (each ficha técnica links to one or more entries from a reusable Plásticos catalog — nombre, sku, color, origen, descripción, armado, dimensión, peso, tipo de empaque, a product photo, and a separate barcode photo — e.g. each of a tangram's 7 pieces; the same catalog entry can be linked into multiple fichas técnicas without duplicating its data, and editing it from one ficha updates it everywhere it's used) and **Imprenta** (printed production data per item — tamaño extendido, tamaño final, tintas, tipo de papel, gramos o puntos, pliego, cortes o tamaño, máquina, formación, número de pliegos, a fixed set of finishing-process checkboxes (Suaje, Guillotina, Plástico, Barniz UV, Barniz de máquina), a freeform list of extra label/value segments for anything not covered by the fixed fields, plus separate Acabados and Notas free-text sections). A third permission, **Configuraciones**, opens an admin panel for managing user accounts/permissions, seeing who's currently connected, and a read-only application event log. Must run on Windows and macOS. Runs against a shared cloud database (Turso/libSQL) so multiple computers in different locations see the same catalog — see "Known constraints" below for the tradeoffs that come with that.

Planned but not yet built: bulk-importing product data from Excel spreadsheets once the shop starts loading their real catalog at volume. No code exists for this yet — when it's requested, it likely means a new Rust command or a JS-side `xlsx` parser feeding the existing `createProduct`/`savePlasticItems`/`savePrintItems` functions, not a new data model.

## Commands

Run from the repo root unless noted. Node and Rust are installed via `nvm`/`rustup` (not Homebrew) — if a fresh shell can't find `node`/`cargo`, source `~/.zshrc` or run:
```
export NVM_DIR="$HOME/.nvm"; [ -s "$NVM_DIR/nvm.sh" ] && . "$NVM_DIR/nvm.sh"
source "$HOME/.cargo/env"
```

Requires a `.env` file at the repo root (gitignored, not committed) with `VITE_TURSO_URL` and `VITE_TURSO_AUTH_TOKEN` — see `.env.example`. These get baked into the built JS bundle by Vite at build time (see "Known constraints" for what that implies). Without it, the app builds fine but every DB call fails at runtime.

- `npm run tauri dev` — run the full desktop app (Rust + webview) in dev mode with hot reload. This is the normal way to test changes, not `npm run dev` alone.
- `npm run dev` — Vite dev server only (frontend in a browser tab). The Turso DB calls in `db.ts` actually work here too (the libSQL web client is plain fetch/WebSocket, no Tauri needed), but anything going through `invoke` (password hash/verify, used for login and for user password changes) or the dialog/fs plugins (image picking) will fail. Useful for search/detail/spec UI iteration; not for login, the permission-gated sections, or image picking.
- `npx tsc --noEmit` — type-check the frontend without emitting.
- `npm run build` — type-check + production Vite build (`dist/`).
- `cd src-tauri && cargo check` — fast Rust compile check without building the full binary.
- No test suite exists yet (frontend or Rust).

### Packaging

Local builds only produce an installer for the host OS (no cross-compiling a Windows .exe from macOS). Both platforms are built via GitHub Actions:
- `.github/workflows/build.yml`, triggered by `gh workflow run build.yml` or pushing a tag matching `app-v*`.
- Produces a draft GitHub Release (`releaseDraft: true`) with `.dmg` (macOS), `.exe`/`.msi` (Windows) attached. Drafts are private until manually published from the Releases page, even though the repo itself is public.
- macOS builds accept the standard Apple signing/notarization secrets in `.github/workflows/build.yml`: `APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`, `APPLE_ID`, `APPLE_PASSWORD`, and `APPLE_TEAM_ID`. Without those GitHub secrets, the build remains unsigned and macOS may report that the app is damaged; for a temporary local install, Control-click the app → Open, or run `xattr -cr "/Applications/Catalogo Imprenta.app"` after copying it to Applications. Windows builds still have no code-signing certificate.
- Repo: `github.com/erosbonoladev/catalogo-imprenta` (public, owner authenticated via `gh` CLI installed at `~/.local/bin/gh`, not Homebrew).
- The workflow passes `VITE_TURSO_URL`/`VITE_TURSO_AUTH_TOKEN` from **GitHub Actions repo secrets** into the build step (same two values as the local `.env`). These must be set once via `gh secret set VITE_TURSO_URL`/`gh secret set VITE_TURSO_AUTH_TOKEN` (or the repo's Settings → Secrets and variables → Actions page) before triggering the workflow — without them the built installers compile fine but ship with no working DB connection.

## Architecture

**Stack**: Tauri v2 (Rust shell + OS webview) + React 19 + TypeScript, database on Turso (hosted libSQL, i.e. SQLite over the network) via `@libsql/client/web`. Chosen over Electron for smaller install size given this ships to end users on both OSes.

**Data layer** (`src/db.ts`): all DB access goes through this one file — no other file touches `@libsql/client` directly. It creates a single module-level client from `import.meta.env.VITE_TURSO_URL`/`VITE_TURSO_AUTH_TOKEN` (see `.env.example`) and exposes typed query functions (`searchProducts`, `getProduct`, `getProductSpecs`, `createProduct`, `updateProduct`, `deleteProduct`, `codigoEnUso`, plus the users/sessions/logs and private-section ones below). Add new queries here, not inline in components. There is **no local SQLite fallback** — no internet means no DB access, full stop; this was an accepted tradeoff for keeping a single source of truth across machines (see "Known constraints").

**Schema** (no migration runner — this is a fresh cloud DB created directly at its current final shape via a one-off setup script, not replayed from history like the old local-SQLite migrations were):
- `products`: `codigo` (unique, this is the search-by-code field), `nombre`, `categoria`, `material`, `descripcion`, `imagen`/`imagen_mime` (BLOB + MIME type, see below), `creado_en`.
- `product_specs`: free-form `etiqueta`/`valor` (label/value) rows per `product_id`, ordered by `orden`. This is intentionally schemaless-ish because different product types (a tangram vs. a banner vs. a business card) need different spec fields — don't add fixed spec columns to `products` for this; add rows here instead.
- `product_plastic_pieces`: superseded by the `plastic_products`/`product_plastic_items` pair below (a one-off migration script copied its rows over). Left in place rather than dropped, same reasoning as other unused tables/columns on this live shared DB. `getPlasticPieces`/`savePlasticPieces` still exist in `db.ts` but are unused — don't resurrect them.
- `plastic_products` (Plásticos catalog, master data): `nombre`, `sku`, `color`, `origen`, `descripcion`, `armado`, `dimension`, `peso`, `tipo_empaque`, `imagen`/`imagen_mime`, `imagen_codigo_barras`/`imagen_codigo_barras_mime`, `creado_en`. One row per reusable plastic product — this is the single source of truth; the same row can be linked into many fichas técnicas via `product_plastic_items` below. `createPlasticProduct`/`updatePlasticProduct` in `db.ts` write directly to this table and are never part of a delete-and-reinsert cycle, so linking/unlinking a ficha técnica never touches or loses this data.
- `product_plastic_items` (Plásticos section, join table): `product_id` (the ficha técnica), `plastic_product_id` (FK into `plastic_products`), `orden`. `getPlasticItems` joins the two tables; `savePlasticItems` in `db.ts` creates/updates the linked `plastic_products` rows first, then fully replace-and-reinserts *only this join table* for the product (same replace-and-reinsert pattern as specs/`user_permissions`, but scoped to the link, not the master data) — removing an item from a ficha técnica ("Quitar de este juego") only deletes its join row, the catalog product itself is untouched and stays reusable elsewhere.
- `product_print_items` (Imprenta section): `nombre` (e.g. "Instructivo"), plus the production fields — all plain `TEXT`, captured as typed by the user, no unit parsing or auto-calculation between them. The `PrintItem` fields in `src/types.ts` don't all match their column names 1:1 (kept for backwards compatibility with rows saved under the old field set): `tamano_extendido` ↔ column `extendido`, `tamano_final` ↔ column `tamano`, `cortes_tamano` ↔ column `corte_cm`; `tintas`, `tipo_papel`, `gramos_puntos`, `pliego`, `maquina`, `formacion`, `numero_pliegos`, `acabados`, `notas` map straight to their same-named columns (`formacion` reuses a column that existed under the old field set; `numero_pliegos` is a newly added column). The table still has older unused columns from a previous field set (`cantidad`, `numero_cortes`, `total`, `merma`, `buenos`, `pliegos_imprimir`, `cada_pliego`, `total_artes`, `existencias`, `total_general`) — left in place rather than dropped (SQLite `DROP COLUMN` on a live shared DB was judged not worth the risk for an early-stage app with near-zero real data), but `db.ts` no longer reads or writes them; don't resurrect them without checking with the user first. Same replace-and-reinsert save pattern as specs/pieces.
- `product_print_item_checks`: exactly five fixed finishing-process checkboxes per print item (`print_item_id`, `nombre`, `marcado` as 0/1, `orden`) — `PROCESOS_IMPRENTA` in `src/types.ts` is the source of truth for the five names (Suaje, Guillotina, Plástico, Barniz UV, Barniz de máquina). `getPrintItems` in `db.ts` normalizes whatever's stored back onto this fixed list/order every time, so the UI never lets users add, rename, or remove a checkbox — only check/uncheck. (This table used to hold freeform user-named checkboxes; that idea is what `product_print_item_extras`, below, replaced it with, just as label/value pairs instead of checkboxes.)
- `product_print_item_extras`: freeform label/value rows per print item (`print_item_id`, `etiqueta`, `valor`, `orden`) — the "+ Agregar otro segmento" button in the Imprenta UI, for whatever production info doesn't fit the fixed fields. Same replace-and-reinsert save pattern as `product_specs`.
- `section_passwords`: leftover from the old per-button password system (see below) — `db.ts` no longer reads or writes it. Left in place rather than dropped, same reasoning as the unused `product_print_items` columns above (not worth a destructive schema change on a live shared DB for near-zero real data). Don't resurrect it.
- `users`: `username` (unique), bcrypt `password_hash`, `activo` (0/1), `rol` (`usuario` | `admin`), `creado_en`. `rol = 'admin'` is a full-access superuser flag checked directly in `hasPermission()` (see below) — an admin row deliberately has no `user_permissions` rows of its own, since its access comes from the role, not from an accumulated checklist.
- `user_permissions`: sparse join table, one row per granted permission (`user_id`, `permiso`) where `permiso` is a free-text string matching one of `PERMISOS` in `src/types.ts` (currently `plasticos`, `imprenta`, `configuraciones`). Adding a new gated area later is just a new string here plus a new `hasPermission(user, "...")` check at the relevant component — no schema change. `fichas_tecnicas` is **not** a row in this table; base catalog access is implicit for any authenticated, active user (see `hasPermission`). `savePermissions`-style replace-and-reinsert on every user save, same pattern as specs/pieces.
- `user_sessions`: `user_id` (primary key — one row per **account**, not per device; the same account logged in on two machines counts as one connection) → `last_seen`. Powers the "usuarios conectados" panel; see the heartbeat description below.
- `app_logs`: `nivel` (`INFO`/`WARNING`/`ERROR`), `mensaje`, `usuario`, `creado_en`. Feeds the read-only Registro tab in Configuraciones. No rotation/trim logic exists yet — same "known constraint, not addressed" posture as other unbounded-growth risks below.

**Autenticación y permisos**: replaces what used to be a per-button password gate (`PasswordGate.tsx`, deleted) with individual user accounts. `src/auth.tsx` is the single source of truth: `AuthProvider` (wraps `<App />` in `main.tsx`) holds the logged-in `CurrentUser` in a React Context, and `hasPermission(user, "plasticos" | "imprenta" | "configuraciones")` is the one function every gated screen calls — never an `if (username === ...)` check. Admin access is `user.rol === "admin"` inside `hasPermission`, short-circuiting to full access; regular permissions come from `user.permisos` (populated from `user_permissions`). Fichas técnicas has no permission check at all — any authenticated, active user reaches it.

Login (`LoginScreen.tsx` → `useAuth().login`) verifies via `verifyLogin()` in `db.ts`, which reuses the same Rust `verify_password` bcrypt command the old system used. On success, `{ id, username }` (never the password or hash) is written to `localStorage`; on every app start, `AuthProvider` re-fetches that user's row fresh from the DB before trusting the session, so a deactivated/deleted account silently falls back to `LoginScreen` even with a stale `localStorage` entry — permissions are never trusted from the cached session. `logout()` clears both.

Every permission-gated screen checks `hasPermission()` **at render time**, independent of how it was reached — `PlasticosSection`, `ImprentaSection`, and `Configuraciones` each render "Acceso denegado" instead of fetching/showing anything if the check fails, rather than relying only on `ProductDetail`/`SearchScreen` hiding the buttons that navigate there. Don't add a new gated screen that skips this — hiding the entry point is not sufficient on its own.

**Usuarios conectados** (heartbeat, not push/websocket — there's no backend to push from): while `user` is set, `AuthProvider` upserts `user_sessions.last_seen` every 20s and opportunistically deletes rows older than 90s; `ConnectedUsersPanel` polls `getConnectedUsers()` every 12s while that tab is actually open. Accepted tradeoffs: up to ~90s lag before a crashed/force-quit client disappears from the list, and the same account on two machines counts once. `logout()` deletes the row immediately, so a normal "Cerrar sesión" doesn't wait out the staleness window.

**Registro (event log)**: `logEvent(nivel, mensaje, usuario)` in `db.ts` writes to `app_logs`, wrapped in a try/catch that swallows its own failures — logging must never break the app it's logging. Called from: login success/failure, permission-denied renders (once per denial, not per re-render), and the existing save-error catch blocks in `ProductForm`/`PlasticosSection`/`ImprentaSection`. `LogsPanel` polls `getRecentLogs()` every 12s and is read-only — it displays event history only, it does not execute anything, and it must stay that way (no command input, no OS shell access).

**Images**: stored directly in the cloud DB as `BLOB` columns (`imagen` + a sibling `imagen_mime` text column), not as local files — this is what makes them show up identically on every computer. Flow: user picks a file via the dialog plugin, `pickImage()` in `db.ts` reads its bytes with `@tauri-apps/plugin-fs`'s `readFile` and returns an in-memory `{ data: Uint8Array, mime }` (`ImageBlob` in `src/types.ts`) → that object is held in component state until the product/piece is saved, at which point the bytes go straight into the `INSERT`/`UPDATE` as a BLOB param. To *display* an image, `getImageSrc()` wraps the bytes in a `Blob` and returns `URL.createObjectURL(...)` — a `blob:` URL, not `convertFileSrc`/the asset protocol (that whole mechanism, and the Rust command `guardar_imagen_producto` that used to copy files into `<app-data-dir>/images/`, is gone). Reading an arbitrary user-picked file's bytes needs `fs:allow-home-read-recursive` in `capabilities/default.json` (see gotcha below) since the picked file can be anywhere under `$HOME`, not just inside the app's own sandboxed dirs.

**Frontend navigation**: no router. `App.tsx` first checks `useAuth()`'s `user`/`loading` — while loading, or with no `user`, it renders `LoginScreen` instead of the rest of the app, which blocks every other screen regardless of `view` state. Once logged in, a `view` union (`search | detail | form | plasticos | imprenta | configuraciones`) in `useState` swaps components manually, same as before. This was a deliberate choice to avoid a routing dependency for a small screen count — don't introduce `react-router` without a reason bigger than "more screens." There's no `gate`/`admin-gate` state anymore — permission checks now live inside the destination screens themselves (see "Autenticación y permisos" above), not in a separate navigation step.

**Save buttons and text inputs**: every editable screen (`ProductForm`, `PlasticosSection`, `ImprentaSection`, `UsersPanel`) follows the same convention now — a `dirty` boolean state, set `true` in every field-update handler and reset to `false` right after a successful save, drives `disabled={saving || !dirty}` on the primary save button; `.btn-primary:disabled` in `App.css` renders that as gray (vs. the normal blue) so the button visually reflects "nothing to save" vs. "unsaved changes." On successful save, components show `src/components/Toast.tsx` (a fixed-position "Guardado con éxito" pill, auto-hides after ~2.5s) instead of inline "Guardado." text — `ProductForm` is the one exception, since it navigates away immediately on save (`onDone`) and a toast would never be seen. Free-text fields use `src/components/AutoGrowInput.tsx` (a `<textarea rows={1}>` that resizes its own height to fit content) instead of raw `<input type="text">`/`<textarea>`, so boxes grow instead of clipping or scrolling; the one exception is `tipo_papel` in `ImprentaSection`, kept as a real `<input>` because its `list=` datalist autocomplete only works on `<input>`, not `<textarea>`. Keep new editable screens consistent with this pattern rather than reintroducing inline "Guardado." text or fixed-height inputs.

**Rust commands**: only `hash_password` and `verify_password` remain (both pure bcrypt, no I/O) — now used for user account passwords (login, create/edit user in Configuraciones) rather than the old section passwords, but otherwise unchanged. Custom `#[tauri::command]`s registered in `invoke_handler!` do not need a capabilities-file entry (unlike plugin commands); only plugin permissions (`dialog:default`, `fs:default`, `fs:allow-home-read-recursive`, etc.) are listed in `src-tauri/capabilities/default.json`. There is no SQL plugin anymore — the DB lives entirely outside Tauri's plugin system, reached over plain HTTPS/WebSocket from the frontend.

**Gotcha already hit twice, same shape both times**: a `<plugin>:default` capability almost never covers everything the plugin can do — it's usually just the "safe"/scoped subset, and the actual permission you need has to be added explicitly by checking that plugin's own `permissions/default.toml` in its crates.io source (unpack the `.crate` tarball from `~/.cargo/registry/cache/.../<plugin>-<version>.crate` if it's not already extracted under `~/.cargo/registry/src/`). First time: `sql:default` (now removed along with the plugin) granted `allow-select`/`allow-load`/`allow-close` but not `allow-execute`, so every write silently failed while reads worked fine. Second time: `fs:default` only grants access to the app's own sandboxed dirs (AppData/AppConfig/etc.), not arbitrary user files — picking an image from Desktop/Downloads/Pictures needed `fs:allow-home-read-recursive` added explicitly. Capability changes need a full rebuild (kill and restart `tauri dev`), not just HMR.

## Known constraints (intentional, not oversights)

- **Multi-machine via a shared cloud DB (Turso), not a traditional client-server setup.** Every install talks directly to the same Turso database over the network — there's no app-controlled backend/API in between. This was a deliberate choice (see conversation history if you need the reasoning) over syncing a raw SQLite file through Dropbox/Drive, which is a known corruption risk when more than one machine has it open at once.
- **The Turso auth token is embedded in the built app at compile time** (via `.env` → Vite → bundled JS) because there's no backend to hold it server-side. Anyone with the compiled `.app`/`.exe` could in principle extract it and get direct read/write access to the whole catalog DB. Mitigation in place: the token was created scoped to only this one database (not an account-wide token), so it's revocable/rotatable from the Turso dashboard without touching code if it's ever suspected of leaking. Don't "fix" this by trying to hide the token differently in the bundle — that's security theater for a statically-shipped desktop app; if stronger isolation is ever needed, that's a real architecture change (an actual backend service brokering DB access), not a small patch.
- No offline mode — no internet means no DB access, full stop. Not addressed; if it's needed later, that's local caching/queueing, a real feature, not a small patch.
- Concurrent-write conflicts (two people editing near-simultaneously) aren't specially handled — last write wins, same as the old local-SQLite version. Accepted as low-risk for this shop's usage pattern; revisit if it becomes a real problem.
- Every authenticated, active user has full read/write access to the base catalog (products/specs/images) — only Plásticos, Imprenta, and Configuraciones are permission-gated. Not a gap: the base catalog was explicitly asked to stay open to all logged-in users.
- "Usuarios conectados" is approximate, not a real presence system — see the heartbeat description above. Up to ~90s of lag on ungraceful disconnects, and multi-device same-account logins are undercounted (counted once). Accepted for this shop's scale; a real presence system would need an actual backend, which is out of scope for the reasons in the Turso-token constraint below.
- `app_logs` has no rotation, trimming, or archival — it grows unbounded for as long as the app is used. Same posture as the other "not addressed yet" items here; revisit if it becomes a real problem (e.g. add a periodic `DELETE ... WHERE creado_en < ...` or a row cap).
- No image optimization/resizing on import — files are stored as-is (now as DB blobs instead of local files, but still unprocessed).
- No Excel import yet — noted above as planned, not started.
- App identifier: `com.mariat.catalogo-imprenta`; product name "Catálogo Imprenta".
